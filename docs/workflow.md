# 運用の流れ：正本 → 生成 → 機械検査 → 人の承認

Curriculum as Code は書式だけでなく、**変更をどう流すか**を決めて初めて効く。

## 1. 正本をバージョン管理に置く

- `curriculum.yaml`（DP 共通定義＋科目定義）を Git リポジトリに置く
- 直接編集してよいのは正本だけ。生成物（シラバス欄・マップ）は編集しない。直したくなったら正本を直して生成し直す
- 学生の成績・個人情報は入れない。リポジトリに入れてよいデータの区分（公開／学内非個人／個人情報）を先に決める

## 2. 変更は差分（プルリクエスト）で出す

- 科目担当者や AI エージェントは正本を直接書き換えず、変更案を出す
- 変更案には「なぜ変えるか」（審議の決定、高等教育機関からの指摘、教員の提案）を書く
- AI エージェントに変更案を作らせる場合、リポジトリの指示ファイル（`AGENTS.md` / `CLAUDE.md`）に守るべきことを書いておく：ID を勝手に振り直さない、既存の DP 名を変えるときは共通定義だけを直す、科目名の表記、など

## 3. 機械検査を自動で回す

- 変更案ごとに `tools/validate.py` を実行し、通らなければ承認に進めない（CI か、AI エージェントのフック）
- 検査するのは形式だけ：無い DP ID・到達目標 ID への参照、配分の合計、重複 ID、許可していない水準語
- 検査が通った変更案に対して `tools/generate.py` を実行し、生成物の差分も見られるようにする（「この DP 名の変更で、シラバス欄が何科目変わるか」が差分で分かる）

## 4. 人が確認して承認する

- 到達目標と評価方法が教育的に対応しているか、DP の水準の置き方が妥当か、は人が読む
- 承認（マージ）は人。AI エージェントは変更案まで
- 承認の記録（誰が・いつ・何を）がそのまま審議の記録になる

## 5. 生成物を配る

- シラバスシステムへの転記、申請書類への貼り込み、学内公開は、生成物から行う
- 生成物には「生成日時と正本のバージョン」を入れておく（どの版から作ったかが後で分かる）

## 一人で始めて、複数人へ

- 最初は一人（カリキュラム担当）が正本を書き、生成と検査を回す
- 二人目が加わるとき、渡すのは正本のファイルと `validate.py` の通し方。各自が別の AI 製品を使っていても、正本と検査は共通にできる
- 残る課題：共通のルール（指示ファイル）を誰が更新し、誰が承認するか。複数人で別々の AI を使うときの版と基準のそろえ方（→ [AcademicOps/docs/06-from-one-to-many.md](https://github.com/shintajiri/AcademicOps/blob/main/docs/06-from-one-to-many.md)）
